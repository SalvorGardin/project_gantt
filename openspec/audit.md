## Исходный анализ: метод и границы проверки

Прочитаны `app.js`, `index.html`, `style.css`, исходный план и инструкции проекта. Анализ выполнен по ponytail full. Синтаксис app.js проверен через Node `vm.Script`. Функции валидатора и поиска циклов выполнены из исходного кода в изолированном контексте с заглушкой списка связей; приложение не изменялось.

Результаты изолированных проверок:

| Вход | Фактический результат |
|---|---|
| Элемент с `start_date: "bad"` | validateImport возвращает null, то есть пропускает |
| `links: {bad: true}` | Пропускает; дальнейший адаптер ожидает массив |
| `schema_version: "invalid"` | Пропускает из-за нестрогого сравнения |
| Связь 2 → 1, проверка добавления 1 → 2, ID — числа | detectCycle возвращает false |
| Та же связь со строковыми аргументами ID | detectCycle возвращает true |

Полный браузерный прогон, визуальная проверка, измерение производительности и проверка экспортированных изображений не выполнялись. Поведение стороннего DHTMLX отмечено как требующее интеграционной проверки там, где его нельзя установить по коду приложения. Сценарии в specs — документированные контракты, не отчёт об успешном E2E-тестировании.

Адаптация на 700/900 px ограничена: toolbar не переносится, часть правил скрытия обращается к отсутствующим span. Поведение на планшете нужно проверить, а не объявлять готовым.

## Предлагаемая структура

Не переносить файлы ради вложенности. Начать с двух самостоятельных границ внутри следующего изменения:

```text
index.html
style.css
app.js                  # инициализация, формы, события, адаптер DHTMLX
js/
  project-file.js        # проверка и подготовка JSON без DOM и глобального gantt
  image-export.js        # захват и обязательное восстановление UI
tests/
  project-file.test.*    # корректные файлы, даты, ID, ссылки, атомарность
openspec/
  specs/
  changes/
  reference/
```

Часть структуры уже реализована: js/project-file.js, tests/project-file.test.cjs и tests/import-browser.cjs. image-export.js ещё не создан. Не выделять одновременно отдельные store/treeView/dependencyManager/historyManager из исходного плана: дерево и связи уже обслуживает DHTMLX, а история ещё не существует. Не создавать вторую изменяемую копию дерева. После появления проверяемой границы файлов при реальной необходимости вынести адаптер DHTMLX отдельно.

Если выбран переход к ES modules, явно закрепить запуск через HTTP и проверить, нужен ли пользователю запуск двойным щелчком по HTML. Если нужен file://, сохранить обычные script-подключения с одним небольшим пространством имён. Не вводить сборщик только ради разделения двух файлов.

CSS пока оставить единым: убрать повторные определения col-progress и перенести статические стили, добавляемые из app.js, в существующие тематические секции. Это отдельная косметическая задача после стабилизации, не повод менять дизайн.

- Создать однодневную задачу, веху и вложенное дерево; изменить сроки; экспортировать и импортировать файл дважды без сдвига дат.

- Изменить только название; открыть новый проект и отменить; отменить импорт поверх изменённого плана; убедиться, что данные не потеряны.
